# Deprecation Policy and Breaking Changes

This document defines the deprecation policy and rubric for breaking changes across the crates in the `rs-soroban-sdk` repository (including `soroban-sdk`, `soroban-sdk-macros`, `soroban-spec`, `soroban-token-sdk`, and related workspace crates).

It sits alongside the version support policy in the repository README to give users and contributors clear, predictable expectations for API evolution, backwards compatibility, and long-term contract maintainability.

---

## 1. Deprecation Policy

### 1.1 Lifecycle Stages

Public APIs evolve through three formal lifecycle stages:

1. **Active / Supported**: The API is current, fully supported, documented, and tested.
2. **Deprecated**: The API is superseded by a newer alternative or scheduled for obsolescence. It remains fully functional, tested, and backwards-compatible. It must not introduce behavioral regressions or unexpected panics for existing callers.
3. **Removed**: The API is excised from the public interface.

### 1.2 Deprecation Standards

When an API is deprecated:

- **Compiler Attribute**: The declaration must carry a Rust `#[deprecated]` attribute detailing the release version and replacement path:
  ```rust
  #[deprecated(since = "X.Y.Z", note = "use `new_function` instead")]
  ```
- **Documentation**: The item's doc comments must include a prominent deprecation notice explaining why the API was deprecated and providing a clear migration example.
- **Migration Path**: An API should only be deprecated when a supported alternative or migration path exists.
- **Release Communication**: Deprecated items must be highlighted in the release notes and `CHANGELOG` under a dedicated "Deprecations" section.

### 1.3 Retention and Removal Timeline

- **Minimum Deprecation Window**: A deprecated API will remain available for at least **one full major release cycle** (or until the subsequent major release boundary).
- **No Removal in Minor or Patch Releases**: Deprecated APIs will **never** be removed in a minor (`vX.Y.0`) or patch (`vX.Y.Z`) release. Removal only occurs upon a major version bump (`v(X+1).0.0`).

## 2. Definition of Breaking Changes

The `rs-soroban-sdk` project adheres strictly to [Semantic Versioning 2.0.0](https://semver.org/) and follows the [Rust API Evolution Guidelines (RFC 1105)](https://rust-lang.github.io/api-guidelines/necessities.html#rfc-1105).

Because `soroban-sdk` operates as both a Rust library and a smart contract development kit with on-chain ABI generation, breaking changes are evaluated across three distinct dimensions:

### 2.1 Rust Language & API Surface

#### Breaking Changes (Require Major Version Bump `v(X+1).0.0`)
- Removing or renaming any public type, trait, struct, enum, function, method, macro, or module.
- Modifying function or method signatures (adding, removing, reordering parameters, or altering parameter/return types).
- Adding a method without a default implementation to an existing public trait.
- Adding fields to a non-`#[non_exhaustive]` public struct.
- Adding variants to a non-`#[non_exhaustive]` public enum.
- Tightening trait bounds on existing generic functions, types, or traits.
- Removing trait implementations from existing public types.
- Modifying public constant values that callers or contract interfaces depend on.

#### Non-Breaking Changes (Allowed in Minor or Patch Releases)
- Adding new public types, traits, functions, methods, or modules.
- Adding a method with a default implementation to an existing public trait.
- Adding fields or variants to items explicitly annotated with `#[non_exhaustive]`.
- Implementing new traits for existing types (provided it does not introduce trait resolution ambiguity).
- Internal refactorings and performance optimizations that preserve external public signatures and semantics.

### 2.2 Smart Contract ABI & On-Chain Spec (Soroban Specific)

Because contracts built with the SDK deploy to the Stellar network and interface with client bindings (e.g. TypeScript, Python) and on-chain callers, on-chain ABI stability is paramount:

#### Breaking Changes (Require Major Version Bump `v(X+1).0.0`)
- Modifying the contract specification XDR output generated by macros (`#[contractimpl]`, `#[contracttype]`, `#[contractclient]`) in a way that breaks existing off-chain clients or cross-contract invocations.
- Altering the serialization, deserialization, or field discriminant ordering of User-Defined Types (UDTs) stored in ledger entries (`ContractDataEntry`).
- Changing the code-generation semantics of `#[contractclient]` such that client call invocations fail against existing deployed contracts.
- Elevating the minimum required Soroban runtime protocol version in a way that makes compiled contracts incompatible with active Stellar network protocol versions.

#### Non-Breaking Changes (Allowed in Minor or Patch Releases)
- Non-semantic dead-code elimination and spec shaking optimizations that reduce WASM binary size without pruning referenced types.
- Additive, opt-in macro attributes that do not affect contracts not using them.
- Diagnostic improvements, error formatting updates, and compile-time validation enhancements.

### 2.3 Test Utilities (`testutils`)

Test utilities (`soroban-sdk/src/testutils`) are compiled under the `testutils` feature or during unit testing:

#### Breaking Changes (Require Major Version Bump `v(X+1).0.0`)
- Removing, renaming, or changing the signatures of public test utility traits (e.g. `testutils::Ledger`, `testutils::storage::*`, `testutils::Events`).
- Changing existing test environment semantics in a way that causes previously valid, conformant contract tests to fail.

#### Non-Breaking Changes (Allowed in Minor or Patch Releases)
- Adding new test helpers, mock providers, or simulation utilities.
- Correcting test utility bugs to conform with documented contract semantics (such as isolating storage inspections to the current contract address).

## 3. Minimum Supported Rust Version (MSRV)

- The Minimum Supported Rust Version for compiling contracts is documented in `README.md` and validated in continuous integration via `make msrv`.
- An MSRV bump is treated as a **minor version change** (`vX.Y.0`), following prevailing Rust ecosystem conventions, provided the new MSRV has been released and stable for a reasonable duration. MSRV will not be bumped in a patch release (`vX.Y.Z`).
